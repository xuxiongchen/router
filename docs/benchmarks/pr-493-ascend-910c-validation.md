# Ascend 910C field validation of Router PR #493

On 19 November 2026 we tested Router commit `00f67f45021024fde7784ce83482110ad326dd73` in seven HTTP serving scenarios. Two explicit-token-ID probes showed agreement between Router prefix credit and actual worker reuse. All 140 routed PD requests delivered the Prefill transfer parameters unchanged to Decode. Decode completed 92 external reads, and 48 requests hit an Ascend connector exception before the read. A completed read also did not guarantee correct text. These results apply to the [tested commit](https://github.com/vllm-project/router/commit/00f67f45021024fde7784ce83482110ad326dd73).

## Configuration and results

Linux AArch64, Ascend 910C, vLLM `0.32.0+empty`, vllm-ascend `0.19.1rc2.dev3401+g28e9e97ba` (clean checkout `28e9e97ba254b076a88275e8a275556cb9a11664`), torch `2.10.0+cpu`, torch-npu `2.10.0.post7`. Regular used two independent TP1/DP1 workers. PD used two independent TP1/DP1 Prefill workers and one TP1/DP1 Decode worker on distinct logical devices. An initial device probe used selectors that resolved to zero devices. The corrected per-process probes each exposed one logical device (about 61.3 GiB total HBM), and all seven runs passed preflight. The fixed-source checks matched for both Ascend connectors and the three inspected vLLM engine files. All PD engines used Ascend `MooncakeHybridConnector`. Router used `--kv-connector nixl` for its pull-response passthrough. This deployment exercises a different protocol path from Router's native Mooncake bootstrap and its connector-specific Prefill lookup cap. ## Where cache evidence stopped

- **Qwen3.8 with MTP.** All participating engines used the requested `qwen3_5_mtp` configuration with three draft tokens. The normalized method was `mtp` and the draft architecture was `Qwen3_5MTP`. Draft/accepted token counter deltas were 4482/2431 and 5046/2757 on the two Regular workers and 11319/11119 on PD Decode. The static layout registered. In both modes the captured warm batch (worker 0, rank 0, sequence 1) held a full-attention store with two 32-byte hashes and 1792 token IDs, plus three Mamba stores. All four stores omitted `lookahead_token_ids`. The offline exporter had populated `hash_lookahead_tokens=1` from the scheduler's Prefill lookahead. The validator rejects a nonempty store without per-hash lookahead tokens under that declaration. Recomputing the two full-attention hashes in each warm sample from the recorded root matched both digests in each run using SHA256 over CBOR of [parent, 896 token IDs, null]; adding the next token to the extra key matched neither. The upstream 0.32 BlockStored schema omits the lookahead field. This identifies a mismatch between our exported declaration and the observed event/hash contract. The 458 Regular and 359 PD `InvalidBatch` warnings include repeats; they are log counts. A corrected validation needs the engine's actual hashing **and** tail-proof semantics with MTP still enabled. The workers recorded `engine_eagle_groups=[3]` (a Mamba group), while this Router revision restricts the explicit nonempty tail-drop list to a supported dense group. [vLLM 0.32 event schema](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/distributed/kv_events.py#L52-L87) · [Store validation](https://github.com/vllm-project/router/blob/00f67f45021024fde7784ce83482110ad326dd73/src/kv_index/source/events/validate.rs#L49-L99) · [Layout admission](https://github.com/vllm-project/router/blob/00f67f45021024fde7784ce83482110ad326dd73/src/kv_index/layout/capabilities.rs#L336-L357) · [vLLM 0.32 hashing](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_utils.py#L941-L998)
- **Qwen3.8 without MTP.** Both Regular workers reported a null speculative method and zero scheduler speculative tokens. With a 1793-token affinity input, worker 0 supplied 1792 cached tokens against 1792 credited. This is a separate control run on the same checkpoint.
- **Qwen3.5 Regular.** The observer captured the warm sequence 1. Router logged a sequence-0 restart and later advanced to sequence 2. The client could not correlate a fresh apply for the warm sequence and skipped the formal routed probe after its timeout. The trace establishes a gap in evidence for this run. The original publisher/replay ordering remains unresolved.
- **DeepSeek mini4.** The runtime layout exposed eight groups, including compressed MLA pages of 512 and 16384 tokens. The normalized layout registered in both modes. The affinity capture recorded zero event frames in either mode and the archived Router logs contained no live sequence advance. With partial hash hits disabled, the engine's cache-hit alignment was 16384 tokens against a maximum context of 10240. A positive backend hit was unreachable under the tested settings. [vLLM hybrid cache alignment](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_coordinator.py#L693-L708)

## Per-request PD transfer and text generation

For each request we matched the P response to the D request, compared the entire transfer object (including grouped block IDs, request ID, host, port and last token), and looked up that remote request ID in the Decode log. The [140-row evidence table](pr-493-ascend-910c-pd-reads.csv) contains a hash of the remote request ID, the producer, the request class, wire line numbers and Decode log line numbers. Each digest is the first 16 hex characters of SHA256 over the UTF-8 remote request ID. Blank log fields mean the corresponding line was unavailable. Counts below include routed smoke, warm-up, affinity probes when issued, and measured requests. Direct Prefill warm-ups are excluded.

| Model | Equal P→D objects | P0 reads / routed | P1 reads / routed | Decode outcome |
|---|---:|---:|---:|---|
| Qwen3.5 | 48/48 | 40/41 | 6/7 | Both 1282-token affinity probes reached D with 1281 external tokens requested. Both failed at block pairing. |
| Qwen3.8 + MTP | 46/46 | 0/40 | 0/6 | Every D request hit a block-pairing exception. No completed read was observed. |
| DeepSeek mini4 | 46/46 | 37/37 | 9/9 | All 46 had positive external-token allocation and a completed read. All four short-answer probes failed. |

**The two Qwen errors occur inside the pinned Ascend connector.** In Qwen3.5 the two long probes each returned four three-entry remote lists. The Mamba lists contained two leading zero blocks. In `group_concurrent_contiguous`, NumPy raised `ValueError: operands could not be broadcast together with shapes (2,) (0,)`. Qwen3.8 returned four singleton remote lists and raised the same error with shapes `(0,) (3,)`. The code compares adjacent differences from remote and local lists. The shapes imply lengths 3 vs 1 and 1 vs 4 respectively in the failing calls. The error occurred before `batch_transfer_sync_read`. D collects unhashed local blocks; the legacy connector trims the remote suffix for non-Mamba groups and skips that trimming for Mamba. Padding in the long Qwen3.5 prompts and the three speculative blocks reserved for Qwen3.8 Mamba groups are plausible explanations for the different lengths. The traceback lacks a group index. The connector catches the exception and enters completion bookkeeping, consistent with the observed HTTP 200 responses. [Ascend transfer loop](https://github.com/vllm-project/vllm-ascend/blob/28e9e97ba254b076a88275e8a275556cb9a11664/vllm_ascend/distributed/kv_transfer/kv_p2p/mooncake_hybrid_connector.py#L684-L705) · [Block pairing and read](https://github.com/vllm-project/vllm-ascend/blob/28e9e97ba254b076a88275e8a275556cb9a11664/vllm_ascend/distributed/kv_transfer/kv_p2p/mooncake_hybrid_connector.py#L792-L819) · [Adjacent-difference check](https://github.com/vllm-project/vllm-ascend/blob/28e9e97ba254b076a88275e8a275556cb9a11664/vllm_ascend/distributed/kv_transfer/kv_p2p/mooncake_hybrid_connector.py#L2174-L2191)

**Generation requires a separate interpretation.** In each Qwen PD deployment, 37/40 benchmark responses were exactly 256 exclamation marks. The other three Qwen3.5 responses had long repeated zeros and the other three Qwen3.8 responses repeated newline/period. Qwen3.5 completed the KV read for all 40 benchmark requests, so the two long-probe transfer failures cannot explain that workload's text degradation. For DeepSeek, the deterministic short-answer failure also reproduced on both directly addressed Regular workers, with repeated end-of-repository markers. This establishes a backend/checkpoint-path reproducer; the cause within that path remains open. The two directly addressed workers and both plain-completion Router formats generated the same short-answer output digest on DeepSeek Regular. A separate Ascend DEBUG logging-format error (`%d` with a `None` value) produced many log messages in DeepSeek PD, including during successful transfers.

## Follow-up for maintainers

For vLLM 0.32 hybrid Mamba with MTP, which runtime fields should an external layout exporter use to derive hash lookahead and tail-drop groups? A small reference declaration for the observed dense group 0 / Mamba groups 1–3 would let us retest the positive cache probe while preserving MTP. For the PD exception, the next isolating observation is the failing group ID and both sides’ block lists immediately before pairing, followed by the same prompt through the pinned engine connector/proxy. For DeepSeek text quality, the direct-worker short-answer reproducer can be investigated independently of routing.
